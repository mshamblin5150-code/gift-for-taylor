# The Schedule book prints from one PDF layout

Printing the Schedule book page had two layouts. Desktops printed `bookPageHtml`, which the browser fitted to the paper at print time with `fitBookPage`. Phones printed `bookPagePdf`, which #239 added because Safari ignored the HTML page's orientation and dropped its borders. Each layout did its own arithmetic, and `bookPageIsHardToRead` warned using the HTML's estimate even when a phone printed the PDF. At 8 Sections, 40 Staff and 15 Shift codes the warning priced about 6.4pt while the PDF printed about 6.9pt. Four print fixes in a row (#230, #235, #237, #239) came from this split. ADR-0010 says printed text is budgeted. This decision from #244 makes that budget one thing rather than two.

**Every device prints the same PDF, laid out by one Dart layout model.** The HTML book page, `fitBookPage`, the iframe printer and the platform check `needsPrintPageGesture` are retired. We chose this over keeping HTML on desktops behind a shared layout model, because the browser fits the HTML at print time. The Dart warning can only estimate that fit, so the two can never agree exactly. With a PDF, the layout that prints and the layout that warns are the same object. Desktops lose one-click printing, and every device now opens the PDF and prints it from the viewer. We chose this over printing the PDF through a hidden iframe where the browser allows it, because a platform branch is exactly how the phone and desktop paths drifted apart. The preview also suits a page she files.

**A Schedule book printing module sits behind one call.** The page calls `prepare(month)`. The module loads the grid, the Shift codes and the month's print wording (ADR-0012), and returns a prepared page: the layout, the effective size of everything on it, and the causes of any small print. The page shows one "Print the book page" dialog, with those causes listed if there are any, and its **Open PDF** button calls `present()`. That button is the tap the browser needs before it will open a window, since preparing is asynchronous. The only adapter operation is presenting PDF bytes: the browser in production, and a recording adapter in tests that records the prepared page. `PrintWordingGateway` and `MonthPrintWordingGateway` become one interface, so the page no longer tells them apart by type.

**Nothing shrinks without the budget knowing.** Text is measured in the bundled font, not estimated per character. The legend wraps into lines at a fixed size, and each line comes out of the grid's height. The name column is sized from the longest measured name, within bounds. A name or code that is still too wide is squeezed sideways, and the squeeze counts: legibility is judged on the smallest effective size anywhere on the page, against the existing 6pt threshold. The warning names what is small and why, worst first, so she can shorten a Shift code meaning or fix a stray code rather than guess. This is still legibility, not content, per ADR-0010.

**Arimo is bundled** in regular, bold and italic, because the PDF's built-in Helvetica only covers Latin-1 and cannot print a name such as "Nguyễn". Arimo has Arial's character widths, so ADR-0010's 80-character title cap and today's look carry over. The typeface belongs to the layout model, so ADR-0009's commissioned print pass can replace it by re-measuring. The page is US Letter landscape only.

The module is a new pure-Dart package, `packages/schedule_book`, depending on `schedule_rules` and `pdf`. `schedule_rules` stays dependency-free, and the package boundary keeps printing runnable under `dart test` and the fixture tool without Flutter. `PrintWording` stays in `schedule_rules`, because it is month data tied to release.

The layout model is the tested contract. `tool/check_book_page_pdf.py` stays as the only check of real output: it reads the rules, fills and text back from a generated PDF. It moves to the new renderer, adds a Vietnamese name and a long legend meaning, and runs in CI.
